KPIS HISTORIAN - PRIMEROS PASOS
==============================

Este proceso consume las evaluations KPI ya confirmadas y materializa dos proyecciones durables en
Parquet: la historia funcional y la historia local de errores. No calcula KPI y no usa pip.

1. ENTRAR AL PROCESO
--------------------
Desde la raíz del repositorio:

    cd scopes/ada/processes/kpis-historian

2. CREAR LA CONFIGURACIÓN LOCAL
-------------------------------

    cp .env.detail .env

APPLICATION identifica el scope compartido del ecosistema, no un namespace privado del Historian.
KPI, Historian y Delivery deben usar exactamente el mismo APPLICATION cuando pertenecen a la misma
solución. Ejemplo:

    APPLICATION=ada-operaciones-integradas-local

El proceso lee y escribe dentro de ese mismo root:

    datasets/kpis/evaluations/               lectura
    datasets/kpis/history/                   escritura funcional
    datasets/kpis/error-history/             escritura diagnóstica local
    .runtime/state/kpis/                     lectura
    .runtime/state/kpis-historian/           escritura

No usa KPI_APPLICATION ni deriva otro APPLICATION.

3. CONTRATO DE HISTORIZACIÓN
----------------------------
- Lee únicamente evaluations inmutables confirmadas por el proceso kpis.
- El techo de consumo es .runtime/state/kpis/committed-watermark.json.
- Mantiene su propio committed watermark en .runtime/state/kpis-historian/.
- Hace catch-up de evaluations reales existentes y conserva sus gaps reales.
- Si existen T1, T2 y T5, procesa T1, T2 y T5; nunca inventa T3 ni T4.
- History materializa todos los resultados con persist_history=true.
- Un resultado ERROR con persist_history=true también queda en history con value y parsed_value nulos.
- Error History materializa todos los resultados ERROR, incluso si persist_history=false.
- Si una evaluation no produce filas en ninguna proyección, igualmente se considera consumida y el
  watermark puede avanzar.
- Ambas escrituras Parquet son idempotentes por (timestamp_utc, key).
- El watermark del Historian avanza solo después de completar ambas proyecciones.
- No modifica datasets/kpis/latest ni el committed watermark de kpis.

4. LAYOUT
---------

    datasets/kpis/history/
        year=YYYY/
            month=MM/
                day=DD/
                    data.parquet

    datasets/kpis/error-history/
        year=YYYY/
            month=MM/
                day=DD/
                    data.parquet

History es vertical y usa el contrato lógico:

    timestamp_utc
    key
    status
    value
    parsed_value

value y parsed_value se codifican internamente como JSON canónico nullable para conservar números,
strings, objetos y arreglos sin imponer un tipo físico distinto por KPI.

Error History es una proyección diagnóstica mínima:

    timestamp_utc
    key
    error

No persiste values, metadata del KPI ni traceback. El error proviene de la evaluation durable y debe
ser seguro para persistencia local.

5. VALIDACIÓN
-------------
La primera vez puedes crear el lock local con:

    uv sync --python 3.14.2

Después:

    scripts/check.sh --clean

El check genera el artifact autónomo en artifacts/processes/kpis-historian y valida Ruff, formato,
tests, wheels internos, lock frozen e import del runtime final.
