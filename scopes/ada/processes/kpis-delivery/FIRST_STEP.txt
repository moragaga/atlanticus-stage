KPIS DELIVERY - PRIMEROS PASOS
==============================

Este proceso consume KPI Latest y la KPI Configuration Projection estable desde Cosmos. Publica
una fotografía Latest orientada por destination_key. No calcula KPI, no historiza y no usa pip.

1. CONFIGURACIÓN LOCAL
----------------------

    cp .env.detail .env

APPLICATION y VOLUMEN_PATH deben apuntar al mismo scope compartido usado por KPI Evaluation.
Para Cosmos se configuran endpoint, key y database. Los contenedores son internos al proceso:

    configuration        -> KPI Configuration Projection
    kpis-latest-delivery -> fotografía Latest de consumo

La proyección de configuración esperada es:

    id = kpis
    partition_key = kpis
    document_type = ada_kpi_configuration_projection

Cada binding utiliza key, destination_keys y latest_enabled. La configuración se lee una sola vez
por job y permanece congelada durante toda la ejecución.

2. CHECKPOINT Y SALIDA
----------------------

El proceso mantiene checkpoint durable propio con el último watermark despachado y la última
revision de configuración despachada. En cada iteración lee el committed watermark de KPI.

Si watermark y revision de configuración ya están confirmados, hace skip sin leer KPI Latest ni
tocar Cosmos de consumo. Si alguno cambió, publica primero la fotografía Latest y sólo después
confirma el checkpoint.

La salida usa:

    id = latest
    partition_id = kpis

manifest.revision es la identidad que debe observar Web para decidir si refresca sus stores.
manifest.watermark_utc identifica la fotografía temporal KPI despachada.

3. VALIDACIÓN
-------------

Desde la raíz del proceso:

    scripts/check.sh --clean

El check valida source, genera artifacts/processes/kpis-delivery, instala el lock frozen del artifact
y verifica el comando ada-kpis-delivery con Python 3.14.2 y UV.
