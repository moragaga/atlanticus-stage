BLOCKGRADE - FIRST STEPS
========================

From the directory that contains "processes":

1. Enter the process:

   cd processes/blockgrade

2. Create the local environment file:

   Linux/macOS:
   cp .env.detail .env

   PowerShell:
   Copy-Item .env.detail .env

3. Complete SQL_CONNECTION_STRING_BLOCKGRADE in .env.
   Do not commit or package the real .env file.

4. Review the source catalog in:

   src/ada/processes/blockgrade/catalog/definitions.py
   src/ada/processes/blockgrade/catalog/tables/

   The current implementation declares dbo.mms_blockgradedetailsbucket. Table participation is
   controlled with enabled=True/False on the source definition. Column definitions remain complete
   and use named parameters; required=True/False expresses the column contract.

5. Create/synchronize the locked Python environment:

   uv sync --python 3.14.2 --frozen

   Do not run "uv lock". The transport bundle already includes its certified uv.lock.
   Do not use pip.

6. Validate one source iteration:

   uv run --frozen ada-blockgrade --run-once

7. Run the complete 10-minute execution normally:

   uv run --frozen ada-blockgrade

NOTES
-----
- Blockgrade captures SQL table change markers once at the start of each execution.
- Each source advances its own producer state independently after successful dataset publication.
- Pending sources are ordered by last successful synchronization.
- The current source reads the current and previous Mine ShiftId through ada-operational-calendar.
- SQL extraction uses mssql-python batches and converts directly to PyArrow; Pandas is not used by
  the Blockgrade process.
- No functional source_last_update column is declared in the current table contract; planning uses
  the technical SQL change marker until a real functional freshness column is confirmed.
- SQL connection/query retries are controlled by BLOCKGRADE_SQL_RETRY_ATTEMPTS and
  BLOCKGRADE_SQL_RETRY_DELAY_SECONDS.
- If the process loses its Atlanticus lease, runtime requests a controlled stop.
